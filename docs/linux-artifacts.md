# Linux artifact catalog and structured interpretation

Research date: 2026-10-11. This is an updateable implementation catalog, not an exhaustive inventory of every Linux application.

The combined index contains 218 specialized artifact definitions: 128 have structured parser adapters and 90 receive raw collection. Media and document extension classifiers continue to operate separately. A path match is a candidate source, not proof of execution, installation, encryption, a complete account inventory, or an active connection.

See [cross-distribution coverage expansion](linux-distribution-coverage.md) for the new definitions, path variants, sources and validation limits. The inventory below documents the earlier core catalog.

## How collection and parsing work

Only regular files found inside selected targets are acquired. Mounted/offline filesystem paths work without consulting the examiner host for user accounts or installed packages. Unreadable sources remain diagnostic errors, not collected evidence. Hash/keyword matching and all-versus-matches-only collection retain their original scope. A verified key/blob/WAL companion needed to interpret a selected database can accompany that evidence, even when the WAL does not independently match a reference.

Structured records retain source paths, SHA-256 hashes, parser identifiers/versions and record locators (table/row, line or byte offset). Sources and unsupported-format notes accompany them. Parsing failures preserve the successfully acquired raw file and are shown explicitly; parser failures and parsed-row totals appear in the scan summary.

SQLite parsing copies verified bytes into RAM and never opens the examined database with SQLite. WAL salts and checksums are validated; only committed pages are applied to the RAM analysis copy. Stale, incomplete or uncommitted tails are reported. Nonempty rollback journals defer parsing. Changes in the database/WAL acquisition window defer parsing. This is a best-effort live snapshot, not a promise that a running application was frozen. A verified nonempty WAL snapshot is retained as companion evidence, with hash/keyword matching preserved.

No examined executable, launcher, service, scheduled job or shell command is run. Supported offline browser credential and encrypted chat formats are decoded using selected-evidence keys or optional local secrets; host keyrings are not unlocked. See [protected format coverage](protected-artifacts.md). XML entities/DTDs are rejected. Native SQLite views/virtual tables are not accepted as expected artifact tables. Epoch timestamps are normalized only when the format establishes their epoch and units. Missing syslog years and local-time zones are not guessed. Linux utmp interpretation currently supports the little-endian 384-byte layout; unsupported layouts fail explicitly.

Files can be parsed beyond the ordinary file-byte cache threshold. Structured decompression/companion reads have explicit safety limits, without restricting raw file acquisition. SQLite snapshots and extracted records require RAM, so very large collections can increase memory consumption. Cancellation is checked during acquisition, replay, query execution and iteration.

## Using the results

Artifact categories remain collapsed until clicked. Double-click a source file to open its **Parsed findings** tab, then select a record for complete fields. The raw source viewer remains available in its own tab. Formats without an adapter display **raw only**. Header-only and configuration-only adapters display **partial**, with their limitations visible; these records are exported with `parser_status: partial` provenance.

Export preserves original files under `evidence/`. Derived records are under `analysis/artifact-NNNNNN/records.jsonl` and `records.csv`, alongside `metadata.json`. JSONL includes input hashes and locators; CSV includes the original source path and SHA-256. The export manifest and PDF describe parser status, record counts/types and limitations. The catalog is included as `analysis/linux-artifact-catalog.json`; all these archive members are covered by SHA-256 verification. Derived records do not replace original evidence.

- `rpm_bdb_inventory`: BDB hash/B-tree RPM headers from verified RAM bytes. Encrypted/checksummed BDB variants and transaction-log recovery are unsupported.
- `rpm_ndb_inventory`: NDB version 0 only; validates indexed blobs and Adler32. No unreferenced/deleted package recovery.
- `rpm_sqlite_inventory`: SQLite Packages headers only; BDB remains raw. Inventory is not proof of execution.
- `snap_inventory`: Persisted snap state; stored revision and active flags are not execution evidence.
- `flatpak_inventory`: Deployment metadata; active deployment cannot be inferred from metadata presence alone.
- `rpm_sqlite_inventory_sidecars`: Raw SQLite companion; verified committed WAL pages are replayed in RAM.
- `desktop_apps`: Launch commands are recorded, never executed.
- `rpm_packages`: BDB and ancillary RPM files retained raw; recognized SQLite/NDB inventories have narrower parser-backed definitions.
